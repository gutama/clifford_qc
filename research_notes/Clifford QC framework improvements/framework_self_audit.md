## Q1. What are the layers and modules of the package, and what does each do?

### Takeaway
The installed package `clifford_qc/` is 126 Python modules / 34,283 lines, organised as Algebra kernel → Program IR → Models → Execution backends → Measurement → Algorithms (VQE/ADAPT) → Subspaces (A-CASE, PRD, QSCI, selected CI, second moments, etc.) → Orchestration → optional Bridges → Evidence tooling. The subspace layer (15,531 lines) dwarfs the algebra kernel (2,368 lines); the codebase is primarily research infrastructure around projected eigensolvers and measurement accounting, not a general simulator.

## Q2. How is the core sparse multivector (`MV`) stored and multiplied; what does it cost; is there any vectorised, bit-packed, compiled or GPU path; what profiling evidence exists?

### Takeaway
`MV` is a Python `dict[int, complex]` keyed by an arbitrary-precision Python integer that packs each Pauli word at 2 bits per qubit. The operator product is a pure-Python double loop over both term dictionaries (O(|A|·|B|) pair products), each pair going through a process-wide `lru_cache`d bit-twiddling kernel that derives X/Z planes and the phase from popcounts. There is no batched/vectorised MV×MV product, no compiled extension (no Numba/Cython/C/C++/Rust), no GPU/JAX path and no multiprocessing in the package. NumPy vectorisation exists only for statevector/sector actions, measurement-compatibility bitsets and packed row storage. Recorded evidence prices memory carefully (85–96 bytes per stored coefficient in the dict representation vs 24 packed) but there is no committed kernel-throughput record.

### Cited Findings
- Storage contract: `MV` has `__slots__ = ("n", "terms")`; `terms` is `dict[int, complex]`; coefficients with `|c| <= TOL = 1e-12` are dropped by the constructor ("Pruning is absolute ... `(1e-7 * X) * (1e-7 * Z)` is therefore the zero operator"); stored components never hold `-0.0`; `MV` defines no `__eq__` ("`X(1, 0) == X(1, 0)` is `False`"; compare with `is_close`) — [clifford_qc/multivector.py:32, 136-183](/home/user/clifford_qc/clifford_qc/multivector.py); [CONVENTIONS.md "Coefficient storage and equality" (line 67+)](/home/user/clifford_qc/CONVENTIONS.md)
- Word encoding: two bits per qubit, `0=I, 1=X, 2=Y, 3=Z`, qubit 0 in the lowest lane (leftmost label character) — [ARCHITECTURE.md "Operator and program boundary"](/home/user/clifford_qc/ARCHITECTURE.md); [clifford_qc/pauli_kernel.py `label_to_code`](/home/user/clifford_qc/clifford_qc/pauli_kernel.py)
- Product implementation (code): `MV.__mul__` loops `for a, ca in self.terms.items(): for b, cb in other.terms.items(): ph, m = _word_mul_unchecked(self.n, a, b); out[m] = out.get(m, 0j) + ca * cb * ph`, then rebuilds an `MV` through the validating constructor — [clifford_qc/multivector.py:240-248](/home/user/clifford_qc/clifford_qc/multivector.py)
- Word-product kernel (code): `_word_mul_unchecked` is `@lru_cache(maxsize=KERNEL_CACHE_SIZE)`; it computes a lane mask, splits each word into `x`/`z` planes (`z = (a>>1)&lo`, `x = (a&lo)^z`), takes `c = a ^ b`, and computes the phase exponent from `bit_count()` of `x&z` terms and `2*(za & xb)` mod 4 — i.e. a symplectic-style formula evaluated on Python big integers one pair at a time. An O(n) per-letter table version `word_mul_reference` is kept as an oracle — [clifford_qc/pauli_kernel.py:153-169 and `word_mul_reference`](/home/user/clifford_qc/clifford_qc/pauli_kernel.py)
- Kernel memo cost (document in code): default cache size 1,000,000 entries per memo; "measured at 12 qubits, a full table is roughly 250 MiB for products and 230 MiB for masks, and a miss costs about twice an unmemoized call, so the table pays for itself only above a ~70% hit rate"; resizable via `CLIFFORD_QC_KERNEL_CACHE_SIZE`; `kernel_cache_info()` / `clear_kernel_caches()` added in the unreleased changelog — [clifford_qc/pauli_kernel.py:15-26](/home/user/clifford_qc/clifford_qc/pauli_kernel.py); [CHANGELOG.md "Added"](/home/user/clifford_qc/CHANGELOG.md)
- The storage ledger prices that memo at a lower bound of 120 bytes/entry, ceiling 120,000,000 bytes (~0.11 GiB), and notes neither packing nor streaming removes it — [benchmarks/reference_results/bank_storage_ledger.json `word_product_cache`](/home/user/clifford_qc/benchmarks/reference_results/bank_storage_ledger.json)
- `memory_estimate()` returns `nnz * (8 + 16)` bytes, which the project itself says "prices the packed representation Phase 2M-B is aiming at", not the dict; `boxed_storage()` returns real dict+boxed-object bytes — [clifford_qc/multivector.py:301-338](/home/user/clifford_qc/clifford_qc/multivector.py)
- Measured cost of the dict representation: 85.24–96.19 bytes per stored nonzero coefficient (pooled 89.92 over 784,792 coefficient occurrences on 7 banks), against the 24-byte packed model, i.e. packing headroom 3.55–4.01× — [bank_storage_ledger.json `measured_rate`, `baseline`](/home/user/clifford_qc/benchmarks/reference_results/bank_storage_ledger.json)
- Packed storage exists (Phase 2M-B): CSR/SoA rows over a shared `GlobalWordTable` (int64 codes, int32 indices, open-addressed slots at ~16 bytes/word vs 101.4 for list+dict), with a generation permutation kept so that floating-point summation order — and hence bit-exact `S`/`H` entries — is preserved; two coefficient layouts (`interleaved` complex128, `soa` float64 pair) are byte-identical — [clifford_qc/subspace/packed.py:1-120](/home/user/clifford_qc/clifford_qc/subspace/packed.py); [packed_bank_storage.json `layout_comparison`](/home/user/clifford_qc/benchmarks/reference_results/packed_bank_storage.json)

- Packing still multiplies through `MV`: rows are packed after the dict product is formed; the packed table's probe loop is Python code over NumPy arrays (`_probe` `while True` loop) — [clifford_qc/subspace/packed.py:108-118](/home/user/clifford_qc/clifford_qc/subspace/packed.py)
- Element-operator cost model (document): complete-SD wall clock "is dominated by the element-operator route, which costs O(|A_i| |H| |A_j|) per pair over M(M+1)/2 pairs and caches every one. - Auditor's ad-hoc measurement (NOT a repository record): on this container (Python 3.13.18, NumPy 2.5.3) a product of two random 1,000-term `MV`s on 14 qubits (10⁶ word pairs, ~998,097 output terms) took 2.23 s with cold kernel caches and 1.43 s warm, i.e. ~1.4–2.2 µs per word-pair product including dict accumulation and constructor validation.

### Inferences
- The kernel is "bit-packed" per word (two Python-int bit planes and popcount phases) but not batched: every pair is a Python function call plus dict insertion, so throughput is bounded at roughly 10⁵–10⁶ pair products per second. Element operators `A_i†HA_j` with |H| ≈ 10³ terms (1,086 for H2O) therefore dominate molecular runtime, consistent with the recorded pair-build shares.
- Because word codes are Python ints, `MV` itself has no qubit-count ceiling, but the packed path stores codes as `np.int64` (packed.py:100,145), which implicitly limits packed storage to 2n ≤ 63 bits (≤31 qubits); `measurement/cache.py` and `measurement/functionals.py` contain explicit fallbacks when `2*n > 63`. No explicit guard in `PackedRowStore` was found (code inference, not documented).
- The memoised word-product cache is a hidden process-global memory cost (up to ~250 MiB at 12 qubits per the code comment) outside every resource ledger; the project now exposes it but does not account it per bank.
- The repository has never committed a like-for-like throughput comparison against any external Pauli-algebra library; its only stated comparison (PauliEngine) is capability-level.

### Gaps
- No committed measurement of word-product throughput, MV×MV scaling with term count, or GPU/compiled alternatives; the R7 profile output is intentionally not stored.
- No record isolates how much of a molecular run is Python interpreter overhead vs inherent O(|A||H||A|) work.

## Q3. What are the largest problem sizes the framework has actually run, and what stops it going further?

### Takeaway
The largest A-CASE (Pauli-bank) runs are 14-qubit STO-3G BeH₂/H₂O full-space Hamiltonians (sector dimensions 1,225 and 441) at basis size M = 31, holding ~92–96 million coefficient occurrences and 7.8 million resident Pauli words, peaking at ~10–11 GiB RSS in the default object representation. All finite-shot/priced measurement studies are at 8 qubits (spin studies at ≤6). Larger numbers exist only for classical sector-vector work (16-qubit 2×4 Hubbard, 4,900 determinants), Stim-only Clifford checks (n=100) and an analytic 4,096-qubit determinant-reference unit test. The binding constraints recorded are Python-object bank memory, O(|A||H||A|) pair construction time, exponential density-MV support under non-Clifford evolution (ADAPT/VQE), and finite-shot statistical unreliability — not qubit count per se.

### Inferences
- The practical ceiling for exact A-CASE in its current Python-object form is ~14 qubits with M≈30 on a 16 GiB host and ~15–140 minutes per run; packing/streaming buy ~3–4× memory at 1.4–4.5× time, so they do not move the ceiling by orders of magnitude.
- The growth driver is the triple-product word universe (|A_i†HA_j| support, millions of words) rather than Hilbert-space dimension: sectors of 441–1,225 determinants are tiny for classical CI, which the molecular report shows CCSD/CISD solving in milliseconds.
- Finite-shot evidence never exceeds 8 qubits, so all measurement-cost conclusions are small-instance.

### Gaps

## Q5. What do the manuscripts' own limitation sections say?

### Takeaway
All five manuscripts disclaim scaling, hardware and quantum-advantage claims; every quantitative result is at ≤8 qubits for sampled/priced work (≤14 for exact A-CASE, ≤4,900 determinants for packet work).
